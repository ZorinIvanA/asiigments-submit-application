# API — бэкенд «Сдача лабораторных работ»

Серверная часть системы: монолитное приложение на **ASP.NET Core** (.NET 8),
которое обслуживает REST API `/api/v1` и раздаёт статику собранного
Angular-клиента (`src/client`). Хранилище — in-memory реализации интерфейсов
репозиториев (см. раздел 5). Подробности —
[Спецификация системы](../../docs/system-specification.md).

Ключевые положения:

- REST API с версионированием в пути: `/api/v1/...`; единый конверт ошибок
  `{message, errors?}` (FR-023)
- Аутентификация: JWT в httpOnly-cookie (access 15 мин + refresh 7 дней);
  CORS не настраивается никогда
- Health-check `GET /health` → `{"status":"ok"}`; Swagger UI только в Development
- SPA fallback: все не-`/api` маршруты отдают `index.html` (с
  `X-Content-Type-Options: nosniff` и `X-Frame-Options: DENY`)
- Конфигурация — только переменные окружения (файлы `appsettings*.json` не
  используются)

---

## 1. Требования и запуск

Требуется **.NET SDK 8.0**.

```bash
dotnet run --project src/api/LabsApp
```

Бэкенд поднимается на **http://localhost:5080** (адрес задан в
`src/api/LabsApp/Properties/launchSettings.json`; переопределяется переменной
`ASPNETCORE_URLS`). При `dotnet run` без явного профиля приложение стартует в
окружении Development; для прод-режима задайте `ASPNETCORE_ENVIRONMENT`.
Проверка живости: `GET /health`; Swagger UI — `http://localhost:5080/swagger`
(только в Development, вне Development `/swagger*` отвечает 404).

Переменные окружения и значения по умолчанию:

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `Auth__JwtKey` | не задана: в Development используется эпизодический случайный ключ (перегенерируется при каждом старте, в журнал пишется warning; токены не переживают перезапуск) | Ключ подписи JWT (HS256). В Production обязательна и должна содержать не менее 32 символов |
| `Auth__AccessTtlMinutes` | `15` | TTL access-cookie в минутах (целое > 0) |
| `Auth__RefreshTtlDays` | `7` | TTL refresh-cookie в днях (целое > 0) |
| `Auth__Pbkdf2Iterations` | `210000` | Число итераций PBKDF2-HMAC-SHA256 для новых хэшей (целое от 1 до 10 000 000; `Verify` читает параметры из самого хэша) |
| `Labs__MaxSemester` | `10` | Верхняя граница номера семестра во всех проверках (целое от 1 до 100) |
| `Seed__TeacherLogin` | `teacher` | Логин сид-учётки преподавателя |
| `Seed__TeacherPassword` | `teacher123!` (только Development; см. предупреждение в разделе 3) | Пароль сид-учётки преподавателя |
| `Seed__DemoData` | умолчание по окружению: Development — `true`, вне Development — всегда `false` | Демо-набор данных; допустимые явные значения — `true` / `false` (некорректное значение даёт warning и умолчание окружения) |

Нарушения правил валидации (например, `Auth__JwtKey` короче 32 символов в
Production или `Auth__Pbkdf2Iterations` вне диапазона) останавливают старт
приложения с сообщением, называющим переменную окружения.

## 2. Схема dev-режима и сборка клиента для прод

**Development** — два процесса:

1. Бэкенд: `dotnet run --project src/api/LabsApp` → Kestrel на
   http://localhost:5080.
2. Клиент: из корня репозитория `npm install && npm start` (`ng serve`) →
   Angular dev-server на http://localhost:4200. Прокси описан в
   `src/client/proxy.conf.json`: пути `/api` и `/health` прозрачно
   проксируются на `http://localhost:5080` (Kestrel), поэтому клиент обращается
   только к собственному origin — CORS не требуется и не настраивается.

**Production** — клиент собирается и раздаётся бэкендом из `wwwroot`:

```bash
npm run build                       # ng build --configuration production → dist/asiigments-submit-application/browser
cp -r dist/asiigments-submit-application/browser/. src/api/LabsApp/wwwroot/
dotnet run --project src/api/LabsApp
```

Копирование сборки в `wwwroot` выполняется вручную (отдельная MSBuild-цель
не предусмотрена). Статику отдаёт Kestrel с защитными заголовками
(`nosniff`, `DENY`); неизвестные не-`/api` маршруты отдают `index.html`
(SPA fallback).

Сборка и проверки (NFR-002 — локальный эквивалент CI):

```bash
dotnet build src/api/LabsApp.sln    # 0 предупреждений (TreatWarningsAsErrors)
dotnet test src/api/LabsApp.Tests/LabsApp.Tests.csproj   # все гейты FR-027
ng build                            # из корня репозитория (клиент)
ng test                             # из корня репозитория, ChromeHeadless
```

## 3. Сид-учётки и предупреждение SEC-001

Сид выполняется синхронно при старте, до обслуживания запросов, и идемпотентен
(повторный запуск не дублирует и не изменяет существующие записи).

**Development:**

| Логин | Пароль | Роль | Примечание |
| --- | --- | --- | --- |
| `teacher` (или `Seed__TeacherLogin`) | `teacher123!` (или `Seed__TeacherPassword`) | преподаватель | создаётся всегда |
| `studentNN` (`student01`…`student32`) | `student123!` | студенты | только при демо-наборе |

Демо-набор (умолчание в Development; `Seed__DemoData=false` отключает):
группы ИК-221 (student01–25), ИК-222 (student26–30), ИК-223 (без студентов),
23 работы (семестр 1 — №1–20, семестр 2 — №1–3) и 4 сид-сдачи.

> **ВНИМАНИЕ (SEC-001).** В окружении **Production** старт приложения
> **блокируется** (fail-fast до сида и обслуживания запросов), если
> `Seed__TeacherPassword` не задана, пуста или равна значению по умолчанию.
> Для прод-развёртывания требуется **собственный пароль**, удовлетворяющий
> правилам пароля системы: длина 8–128 символов, обязательно цифры, буквы и
> специальный символ (пароль не тримуется). Значение по умолчанию для
> прод-развёртываний намеренно не документируется — не используйте значения
> из этого README в Production. Дополнительно в Production обязательна
> `Auth__JwtKey` (не менее 32 символов), а cookie получают флаг `Secure`.

## 4. Оперативная заметка: KDF-поверхность и алертинг

Каждая операция вывода ключа (PBKDF2-HMAC-SHA256,
`Auth__Pbkdf2Iterations`, по умолчанию 210 000 итераций) инкрементирует
метрику `auth_kdf_operations_total{caller}` (caller ∈ `login`, `register`,
`reset_password`, `change_password`, `seed`, `reference`); суммарное значение
логируется раз в 60 секунд. Реестр остаточных KDF-поверхностей (FR-004,
оценки SEC-002):

- **вход** (`POST /auth/login`): ≈ `MaxTrackedKeys` × 5 = 10000 × 5, т.е.
  вход: ≈50000 KDF/мин (≈833/с) устойчиво с одного IP при ротации логинов
  (каждый ключ «логин|IP» выдерживает 5 неудачных входов за 60-секундное
  окно); обновляется каждый период окна. Поверхность ПРИНЯТА осознанно:
  пер-IP сдерживание в этой итерации заморожено, остаточная поверхность
  неуспешных входов, распределённых по ключам, сохраняется;
- **регистрация**: ≤ 5 KDF/час с одного IP (KDF только при успешном создании
  учётки; до создания — валидация и 409);
- **восстановление пароля** (`recovery/request`, `recovery/confirm`):
  0 операций KDF (коды и reset-токены хэшируются быстрым солёным SHA-256),
  амплитуда CPU пренебрежима;
- **смена/сброс пароля** (`reset-password`, `me/password`): KDF только после
  предъявления валидного токена/валидной сессии — неаутентифицированная
  амплитуда 0.

Иные (неаутентифицированные) KDF-поверхности в системе запрещены.

**Алертинг:** порог `auth_kdf_operations_total` **> 100/с в течение 5 минут**
— признак перебора; при штатной работе интенсивность на порядки ниже.

Частотные границы (матрица FR-004): неудачные входы — 5/60 с на ключ
«логин|IP» (проверка выполняется только на ветке неудачного пароля, после
ровно одной KDF); регистрации — 5/3600 с на IP (учитываются все попытки);
запросы кода восстановления — 3/3600 с на email. Превышение → 429 с телом
`{"message":"Слишком много попыток. Повторите позже"}`.

## 5. Хранилище: in-memory сейчас, EF Core/PostgreSQL — следующая итерация

Сейчас данные живут в памяти процесса: репозитории
`IUserRepository`, `IGroupRepository`, `ILabRepository`, `ISubmissionRepository`,
`ISecurityTokenRepository` реализованы in-memory (состояние теряется при
перезапуске). Контроллеры и ядро аутентификации зависят только от интерфейсов,
поэтому переход на **EF Core + PostgreSQL (Npgsql)** выполняется в следующей
итерации заменой in-memory реализаций этих интерфейсов на persistence-реализации
без изменения доменной логики и контрактов API. В текущей итерации EF Core и
Npgsql не используются.

## 6. Dev-почта (восстановление пароля)

- **Development:** письма восстановления отправляются только в журнал —
  категория `EmailDev`, каждая запись с маркером `[DEV-EMAIL]` и полным текстом
  письма (адресат, тема, код восстановления). Это **единственное место**, где
  код восстановления появляется.
- **Остальные среды:** письмо не отправляется и не логируется (заглушка пишет
  один warning без адресата и содержимого); код восстановления вне категории
  `EmailDev` не появляется никогда.

Эндпойнт `POST /auth/recovery/request` отвечает `200` с пустым телом
независимо от существования email (оракула нет) — см. журнал `EmailDev`, чтобы
увидеть письмо в Development.
